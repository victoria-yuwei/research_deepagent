
# 知识点总结

## 一、direnv 环境变量管理

### 1. 核心机制
direnv 是 shell 的环境变量管理器，通过 hook 进 bash/zsh/fish，根据当前目录自动加载或卸载环境变量，实现项目级隔离，避免污染 `~/.profile`。每次提示符前它会检查当前及父目录是否存在 `.envrc`，若存在则加载进子 shell，捕获所有导出变量后注入当前 shell，同时移除被 unset 的变量。

### 2. 安装与 Shell 集成：怎么在一个项目里默认进入某个虚拟环境

```bash
# 1. 安装
brew install direnv

# 2. 挂载 hook（Zsh）
echo 'eval "$(direnv hook zsh)"' >> ~/.zshrc
source ~/.zshrc shiganma de
（source ~/.zshrc 的意思是：把 ~/.zshrc 这个文件里的命令，在「当前这个 shell」里重新执行一遍。）
# ★ 关闭终端窗口，重新打开（不要只用 source）

# 3. 验证 hook
type direnv          # 应显示 "direnv is a shell function"

# 4. 进项目目录
cd /你的项目目录

# 5. 创建虚拟环境（先建好，或靠 .envrc 自动建）
python3.11 -m venv myenv

# 6. 在项目下面创建一个.envrc的文件
touch .envrc
# 用nano命令打开
nano .envrc
# 写入内容
改成这个：
# 1) 激活已有的 myenv 虚拟环境
export VIRTUAL_ENV="$PWD/myenv"
export PATH="$VIRTUAL_ENV/bin:$PATH"
# 2) 加载 .env 里的密钥
dotenv
# 保存和退出
ctrl+o保存，ctrl+X退出

# 7. 创建 .env 并填密钥
touch .env
nano .env
#   写入 KEY=VALUE，Ctrl+O → 回车 → Ctrl+X

# 8. 加 .gitignore
printf ".env\n.direnv/\nmyenv/\n__pycache__/\n" >> .gitignore

# 9. 授权
direnv allow

# 10. 验证
cd .. && cd 项目目录
which python                  # → .../myenv/bin/python
echo $SILICONFLOW_API_KEY     # → 你的密钥
```
什么叫做挂载？（Hook）
Linux：把一个磁盘设备接入到文件系统，但是在direnv语境中，意思是劫持或者植入。让Zsh每次都能联想到direnv这个独立的小软件，可以使用这句命令：eval "$(direnv hook zsh)”，可以把 direnv 的核心逻辑“塞”进 Zsh 的生命周期里

授权成功的唯一判据：
`direnv allow` **必然打印** `direnv: loading` 和 `direnv export: +VAR`。静默无输出说明命令没走到加载环节。

`.envrc` 同时管 venv 和密钥
虚拟环境：目的是让每一个项目使用的python版本不打架。需要每次开终端的时候都敲一下source。想省事的话，用 IDE 解释器设置、direnv 自动激活，或全路径调用。

### 4. 终端为什么叫做Zsh？
黑框框Terminal不是Zsh，只是显示器；真正负责解析指令、打印结果的程序是Shell；Mac中自带的Shell有很多种，最古老的叫做bash，从macOS Catalina开始，苹果把默认的Shell换成了Z shell，也就是Zsh
「echo $SHELL 看看，如果输出是 /bin/zsh，说明你正在用 Zsh 干活」

### 5. 环境叠加规则
**Python venv 不能同时进两个**：解释器只有一个，`which python` 只能指向一个路径，两个 venv 的 `bin/` 同时进 PATH 会导致排在前面的赢。direnv 是**单环境替换**机制，只加载向上找到的第一个 `.envrc`，加载新的之前先卸载旧的。

环境变量配置**可以合并**：
```bash
source_up                          # 先加载父目录 .envrc
source_env_if_exists .envrc.local  # 再加载本地私有覆盖
```

## 二、Shell 变量赋值语法

### 1. 核心规则
`NAME=value` 中间**不能有任何空格**。

```bash
export NAME = value    # 错：等号两边都有空格
export NAME =value     # 错：等号左边有空格
export NAME= value     # 错：等号右边有空格
export NAME=value      # 对
export NAME="value"    # 对，值含特殊字符时推荐
```

### 2. `export KEY= "value"` 的报错原理
shell 把它切成两个参数：
- `KEY=` -> 把**空字符串**赋给 `KEY`
- `"tvly-..."` -> 被当成**第二个变量名**

变量名只能由字母、数字、下划线组成，含连字符 `-` 非法，故报错。

> `export: not valid in this context` 是 **zsh 特有**文案，bash 同样情况报 `not a valid identifier`。

### 3. 最阴险的坑
`export NAME= value` 会**静默地把空字符串赋给 NAME**，然后才因第二个参数非法而报错。若第二个参数恰好是合法变量名，命令**完全不报错**但 `NAME` 是空的——极难排查。

### 4. `.env` vs `.envrc` 格式差异

| 文件 | 写法 | 原因 |
|---|---|---|
| `.env` | `KEY="value"` | 给 dotenv 解析器读，纯键值对 |
| `.envrc` | `export KEY="value"` | 给 shell 执行，需要 `export` |

### 5. 手动 export 与 direnv 冲突
手动 `export` 只对当前终端窗口生效，且 `cd` 进出目录触发 direnv 重载时，**`.env` 里的值会覆盖手动值**。正确做法是改 `.env` 后 `direnv allow`。

## 三、LangChain 中间件

### 1. 能力扩展类中间件一览

| 中间件 | 说明 |
|---|---|
| `TodoListMiddleware` | 任务规划与跟踪 |
| `FilesystemMiddleware` | 文件系统中间件 |
| `SubAgentMiddleware` | 子代理 |
| `ShellToolMiddleware` | Shell 工具 |

### 2. TodoListMiddleware 工作机制
```python
from langchain.agents.middleware import TodoListMiddleware

agent = create_agent(
    model=model,
    tools=[],
    middleware=[TodoListMiddleware()],
)
```
启用后发生三件事：
- **注入 `write_todos` 工具**：Agent 获得专用工具创建/更新任务列表
- **持久化 `todos` 状态**：任务列表作为 Agent 状态的一部分保存，跨轮次存活
- **引导 Agent 使用**：自动注入系统提示词，引导 Agent 遇复杂任务主动规划

### 3. 任务状态流转
每个子任务条目含 `content`（任务描述）和 `status`（状态），状态共三种：

| 状态 | 含义 |
|---|---|
| `pending` | 尚未执行 |
| `in_progress` | 当前正在执行 |
| `completed` | 已完成 |

Agent 严格按列表顺序执行：当前子任务标记进行中 -> 完成更新为已完成 -> 自动推进下一个 pending，循环至全部完成。

### 4. 关键安全限制
`write_todos` **每轮模型调用最多只能被调用一次**。因为它会**替换整个任务列表**，若允许并行调用，后一个调用会完全覆盖前一个，造成混乱。

### 5. 适用场景

| 适合 | 不适合 |
|---|---|
| 任务需要 3 个或更多明确步骤 | 简单的单轮问答（增加不必要开销） |
| 任务耗时较长，需结构化跟踪进度 | |
| 需在前端实时展示动态进度面板 | |

### 6. 为什么需要它
Agent 执行多步骤、跨工具复杂任务时，若无规划能力容易在步骤中迷失或忘记已完成部分。Trae、Claude Code 等编程智能体接到复杂任务时，首要工作往往是生成清晰的任务规划清单。

### 7. 前端集成
`useStream` 钩子通过 `stream.values.todos` 公开状态，UI 响应式渲染。没有 `TodoListMiddleware` 时不存在 `stream.values.todos`。

### 8. 观察动态变化
用 `invoke` 同步调用时，Agent 执行完所有任务才返回，最终打印的所有子任务状态均为 `completed`。若想观察 `pending -> in_progress -> completed` 的流转，需用**流式输出**。

## 四、FilesystemMiddleware 核心要点

### 1. 三层能力
- **提供文件系统工具**：注入标准文件操作工具
- **自动上下文卸载**：任何工具返回结果超过 token 阈值（默认 20000）时，自动写入虚拟文件系统，上下文中只留截断预览和文件引用，防止上下文窗口被撑爆
- **可选安全执行环境**：若后端实现 `SandboxBackendProtocol`，额外注入 `execute` 工具，允许在隔离沙箱中运行 shell 命令

### 2. 内置工具

| 工具 | 作用 |
|---|---|
| `ls` | 列出目录内容 |
| `read_file` | 读取文件完整内容或指定行范围 |
| `write_file` | 创建或覆盖文件 |
| `edit_file` | 精确字符串替换或编辑 |
| `glob` | 按文件名模式查找 |
| `grep` | 在文件内容中搜索正则匹配 |
| `delete` | 删除文件或目录 |
| `execute` | 仅沙箱后端可用，运行 shell 命令 |

### 3. 关键参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `backend` | `StateBackend`（临时存储） | 定义文件存储位置，决定持久性和执行能力 |
| `tools` | `None`（全部工具） | 工具白名单，限制 Agent 可用的文件操作 |
| `tool_token_limit_before_evict` | `20000` | 工具结果卸载阈值 |
| `human_message_token_limit_before_evict` | `50000` | 人类消息卸载阈值，防止超长粘贴撑爆上下文 |
| `permissions` | `None` | 路径级权限控制，保护敏感文件（如 `.env`）的关键 |
| `max_execute_timeout` | `3600` 秒 | `execute` 工具命令执行超时 |
| `grep_max_count` | `1000` | grep 返回最大匹配数 |

## 五、pip / uv / poetry 三种装包方式对比

| 工具 | 定位 | 特点 |
|---|---|---|
| pip | Python 官方自带包安装器 | 最通用、生态最全，但慢，只装包、不管虚拟环境和锁文件 |
| uv | 新一代 Rust 写的包管理器 | 极快，兼容 pip 用法，能顺带管 Python 版本和虚拟环境，`uv pip install ...` 可平替 pip |
| poetry | 项目级依赖与打包管理工具 | 用 `pyproject.toml` + `poetry.lock` 锁定精确版本，强调可复现，适合正式项目协作 |

**选择建议**：临时装包用 pip 或 uv；追求速度用 uv；正式项目要锁版本、团队协作、可复现用 poetry。

## 六、虚拟环境的本质与激活方式

- **本质**：把 Python 想成装了全局包的大房间，所有项目共用一套库会打架（A 要 `foo==1.0`，B 要 `foo==2.0`，全局只能存在一个）。虚拟环境是给每个项目单独隔出的小房间，含独立解释器副本和自己的包目录，项目间互不干扰，删目录即干净卸载。
- **默认激活方式**：激活只对当前 shell 进程生效，**新开终端窗口或重新 `cd` 进来都需重新激活**。
- **direnv 自动化**：在项目 `.envrc` 写：

```bash
export VIRTUAL_ENV="$PWD/myenv"
export PATH="$VIRTUAL_ENV/bin:$PATH"
```

执行 `direnv allow` 后，`cd` 进目录自动带上 `myenv`，`cd` 出去自动还原。前提是 direnv 的 shell hook 已正确配置，且改完配置要**关掉终端窗口重开**（`source` 配置文件往往挂不上钩子）。


## 七、`import os` 与 `os.environ`：把密钥外置

- **目的**：`import os` 不是为了"从别的函数里调用"，而是为了让当前文件能用 `os.environ` 读取**环境变量**。
- **两种取值方式**：
  - `os.environ.get("MODEL_NAME", 默认值)`：读 `MODEL_NAME`，没设则用默认值。
  - `os.environ["SILICONFLOW_API_KEY"]`：直接取值，没设会抛 `KeyError`。
- **设计意图**：把 API key、模型名等敏感或可变信息放到代码外面（操作系统环境变量），而非硬编码进源码。运行前需先 `export SILICONFLOW_API_KEY="你的密钥"`。

## 八、`from mymodule import my_function`：导入 ≠ 调用

- **准确含义**：从 `mymodule` 模块里把 `my_function` 这个名字**引入当前命名空间**，之后可直接写 `my_function()`，不必写 `mymodule.my_function()`。
- **关键区分**：**导入是"拿到"，调用是"执行"**。`import` 那行只是把函数引进来，不会运行它；真正执行是后面写 `my_function()` 时。
- **等价写法**：

```python
from mymodule import my_function          # 直接导入函数
import mymodule                           # 导入整个模块，用 mymodule.my_function()
from mymodule import my_function as mf    # 导入并起别名
```

## 九、脚本 vs 模块：同一文件的两副面孔

- **核心认知**：`mymodule.py` 被 import 当模块用，**不是说它从此不能当脚本**。同一 `.py` 文件始终有两种用法，取决于怎么用：
  - `python mymodule.py` → 当作**主程序（脚本）**运行，`__name__ == "__main__"`。
  - 别的文件 `import mymodule` → 当作**模块**加载，`__name__ == "mymodule"`。
- 两种方式互不排斥，文件本身没变，只是"角色"不同。
- **标准写法**：用 `if __name__ == "__main__":` 把"只在直接运行才执行"的部分包起来：

```python
def my_function():
    return "hello"

if __name__ == "__main__":
    print(my_function())   # 只有 python mymodule.py 时才执行
```

直接运行会打印 `hello`；被 import 时只交出 `my_function`，不会误执行。

## 十、顶层代码与导入副作用

- **顶层代码定义**：一个 `.py` 文件里**顶格写、不属于任何函数或类**的语句。`import` 一个文件时，Python 会把它的顶层代码**从头到尾真的执行一遍**。
- **定义 vs 执行**：
  - `def my_function(): ...` 这行顶层代码执行的是"**创建函数对象并绑定到名字**"，函数体里的代码不会跑。
  - `print(...)`、`x = 10` 这类顶层代码则是"**真的做这件事**"。
- 因此 import 后能用 `mymodule.x`、`mymodule.my_function`，因为顶层代码已把它们创建好；但函数体不会因 import 而运行——那是**调用**时才发生的。
- **导入副作用坑**：若顶层写了 `result = my_function()` 或 `print(...)`，别人 `import mymodule` 时会真的触发调用和打印。凡不希望"被 import 就触发"的逻辑，都应放进 `if __name__ == "__main__":` 里。
